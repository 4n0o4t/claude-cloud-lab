# 动效与交互

## 读取条件

用于状态反馈、导航转场、复杂滚动、动画图表、Canvas、3D 或动效库选型。静态布局任务不读。

## 动效职责

每段动效至少表达一种含义：

- 状态：加载、完成、失败、选中、展开。
- 因果：说明哪个操作引发了变化。
- 方向：进入、返回、前进、切换层级。
- 连续性：保留对象、布局或上下文之间的关系。

不能说明含义的漂浮、视差、逐元素淡入默认删除。高频操作反馈要短，低频品牌或叙事场景才允许更强编排。

## 实现选择

选择能完成目标的最轻方案：

- CSS transition / animation：hover、focus、展开和简单状态。
- Web Animations API：需要程序控制但规模较小的动画。
- Motion 类框架：组件进出、共享布局和常规 scroll-linked 动画。
- GSAP：复杂时间线、精确同步或高强度叙事编排。
- Three.js / WebGL：实时空间、着色器或图形计算是体验本身时才使用。
- 平滑滚动或虚拟滚动：原生滚动无法满足明确目标时才引入，并保留可访问替代路径。

库的知名度不是引入理由。选型同时评估包体积、主线程开销、移动端性能、SSR/hydration、维护成本和无动画降级。

## 硬边界

- 动画不能阻塞关键操作，也不能让按钮、输入框或内容在交互时改变尺寸。
- 页面和状态切换优先保留共享结构，避免无意义闪烁和整体重排。
- 支持 `prefers-reduced-motion`；重要信息不能只通过运动表达。
- hover 必须有键盘和触摸可用路径；手势交互要有可发现的控制或提示。
- 自定义滚动不得破坏返回、锚点、焦点、选择文本和滚动条预期。
- 连续快速操作、动画中断、路由返回和低性能设备都要得到确定结果。

## 交付自检

- 动效解释了什么状态、因果、方向或关系？
- 去掉它会损失理解，还是只损失装饰？
- reduced motion、键盘与触摸路径是否完整？
- 快速重复操作后，界面是否停在正确状态？
- 是否有更轻的原生或 CSS 方案？
